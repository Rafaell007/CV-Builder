# Apollo

Apollo Client 4 with the Next.js App Router integration (PLAN D6, D8). Operations and their types come from `@/shared/graphql` (codegen).

- `@/shared/apollo` → `ApolloClientProvider`: wraps the app in `app/layout.tsx`. Client Components then use the hooks from `@apollo/client/react`. Requests go to the frontend's own `/graphql`, which Next.js rewrites to the backend, so the browser sends the auth cookies itself.
- `@/shared/apollo/server` → `query`, `getClient`, `PreloadQuery`, `PrefetchQuery`: for Server Components. A new client per request calls `BACKEND_URL` directly and forwards the request's cookies (`cookieLink`). The data is per request, so a Server Component that queries starts with `await connection()` (from `next/server`) and is rendered inside `<Suspense>`; otherwise Cache Components tries to prerender it at build time and the build fails. `PreloadQuery` fetches on the server and hands the result to a Client Component's `useSuspenseQuery`, so protected data never needs cookies in the browser bundle.
- `PrefetchQuery` (KAN-172): how a protected page renders its data on the server (PLAN D6). `<PrefetchQuery query variables>` runs the query with the user's cookies (`PreloadQuery`, `errorPolicy: "all"`) and renders its children inside `WaitForQuery`, which suspends until the result is in the browser's Apollo cache. The children keep their own `useQuery`: with the same query and variables it reads the cache, also during the server render, so the server HTML has the data and the browser sends no request for it. Search, sort and page changes then go to the backend from the browser, as before. A plain `useQuery` under `PreloadQuery` is not enough: during the server render it only reads the cache and shows its loading state, so the data would sit only in the RSC payload. A failed query does not throw: the server HTML shows the loading state, and the children's hooks send the query again in the browser and show their own error. It must render inside `<Suspense>`: the `(app)` layout has one around every protected page, and a page adds none of its own. Such a page declares `export const instant = false` (a navigation to it may wait for the data; the Next.js dev check asks for it). Measured on client navigations: with the layout's boundary React keeps the old page until the new one is ready (rows at about 50 ms); a boundary inside the page shows its loading state first, and React keeps it for at least 300 ms (rows at about 340 ms). Used by the list routes (`/users`, `/cvs`, `/admin/*`) and the admin layout.
- `errorLink`: shared by both clients; logs GraphQL and network errors. `NOT_FOUND` and `FORBIDDEN` are logged as warnings, because the pages show a screen for them.
- `createSessionLink`: browser client only. A request that fails with `UNAUTHENTICATED` triggers one session refresh (`refreshSession`, single-flight), then runs again once. If the refresh is refused, or the second run fails the same way, it redirects to `/sign-in`, and the request stays pending until the browser leaves. So the page keeps its loading state and shows no error screen first. When there is nowhere to redirect (the user is on `/sign-in`), the error reaches the caller. A network error during the refresh signs nobody out. `SignIn`, `SignOut` and `Refresh` are skipped. On the server the proxy has refreshed the session already (see [session](../session/README.md)).
- `networkErrorLink`: browser client only. A **query** that cannot reach the server (fetch failed, or a 5xx status) calls `markQueryFailed()` from [network](../network/README.md), so the No Internet screen shows. Mutations, 4xx and GraphQL errors are ignored. It runs before the session link, so it sees only the final error.

Docs: [Apollo, Next.js App Router](https://www.apollographql.com/docs/react/integrations/nextjs), [Apollo Client 4 migration](https://www.apollographql.com/docs/react/migrating/apollo-client-4-migration).
