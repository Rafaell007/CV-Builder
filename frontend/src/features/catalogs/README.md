# Catalogs

The `/admin/departments`, `/admin/positions` and `/admin/skills` pages (PLAN S5.1, S5.2, S5.3; KAN-96, KAN-98): the global lists of departments, positions and skills, for Admin users. Each page lists, searches, sorts (by name) and pages on the backend, and creates, updates and deletes one item. A department or position has a name only; a skill has a name and a category, and shows the category's type.

- Exports (`index.ts`): `Departments`, `Positions`, `Skills` (the page bodies).
- Texts: `messages/en.json`, `pl.json` (namespace `catalogs`). `departments`, `positions` and `skills` share their keys, so the shared parts take the namespace `catalogs.departments`, `catalogs.positions` or `catalogs.skills` (`CatalogNamespace`) and work for all three. `skills` has extra keys for its columns and the Category field.
- Shared by all catalogs (everything except the GraphQL wiring and the skill form):
  - `catalogs.types.ts`: `CatalogNamespace`, `CatalogItem` (`id`, `name`), `CatalogNameFormValues`.
  - `catalogs.constants.ts`: `CATALOG_SORT_FIELDS`, `DEFAULT_CATALOG_SORT` (name ascending; the backend sorts by name only), `MAX_CATALOG_NAME_LENGTH` (100, as the backend), `CATALOG_SEARCH_MAX_LENGTH`.
  - `utils/`: `catalogNameSchema` (the name rules) and `isCatalogConflict` (a `CONFLICT` error: on create or update the name exists; on delete the item is in use).
  - Hooks: `useCatalogNameForm` (the form), `useCreateCatalogItemForm(ns, create)`, `useUpdateCatalogItemForm(ns, update)`, `useDeleteCatalogItem(ns, remove)`: they take the catalog's mutation function and show the toasts and error texts. Save is enabled only when the trimmed name differs from the original (`hasChanged`). A delete of an item in use keeps the confirmation open and shows the "in use" text inside it (`error`); other delete failures close it and show a toast.
  - Components: `CatalogTable` (the Name column, optional `extraColumns` and the row menu), `NameFormModal` (one-field modal, kind `create` or `update`), `DeleteCatalogItemModal`, `CatalogPage` (`ListPage` + table + the Delete modal; each catalog passes its Create/Update modals in `modals` and opens them via `onCreate`/`onEdit`; after the only row of a later page is deleted it goes back one page, and shows the loading state, not the empty state, in between).
- Per catalog (`components/Departments/`, `components/Positions/`, `components/Skills/`, the same shape): `useDepartments` / `usePositions` / `useSkills` (the list query through the shared `usePagedList`), `useCreateX`, `useUpdateX`, `useDeleteX` (each with its `.graphql` file), and `X.tsx`, which passes them to `CatalogPage`. Test data: `x.mocks.ts`, thin files over the shared factory `createCatalogMocks` (`catalogs.mocks.ts`, with its test).
- Skills only (`components/Skills/`): the Type and Category columns (`extraColumns`), `useSkillCategories(enabled)` (the Category options, loaded only while a modal is open), `useSkillForm` (name + category, `hasChanged` on the trimmed name or the category), `useCreateSkillForm`, `useUpdateSkillForm` and `SkillFormModal` (Name field + Category select). The type is not sent: the backend takes it from the category. `skills.mocks.ts` adds its own create, update and category mocks, as these send a category.
- Used by: the routes `app/[locale]/(app)/admin/departments`, `admin/positions` and `admin/skills` (`PageHeader` + the page). E2E: `e2e/catalogs/` (`skills.spec.ts` has its own tests, as its seed has more than one page and its form a Category field).
