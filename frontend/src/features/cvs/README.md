# CVs

The `/cvs` page (PLAN S7.1b, KAN-112): the list of CVs. An Employee sees own CVs, an Admin sees all CVs. The backend decides which rows each role gets.

- Exports: `Cvs` (the page content). The route renders the `PageHeader` (top bar with `CVs`) above it; `Cvs` uses the shared `ListPage` (sticky toolbar with search and CREATE CV, page buttons; KAN-96). As in Figma, the CVs create button centres its icon and text (8 apart), and on `/cvs` it is 120 from the right edge (the User CVs tab: 20), set with the `ListPage` CSS variables in `Cvs.module.css`. Optional props: `userId` (the CVs of one user, for the User CVs tab) and `onView(cv)`. `Cvs` owns the Create, Update and Delete modals (see below).
- List state: the shared `useListState(DEFAULT_CVS_SORT)` (`@/shared/lists`) holds the choices of the user: `search`, `sort` and `page`. A new search or sort goes back to page 1. Nothing is filtered or sorted in the frontend.
- `utils/toCvsVariables`: the shared `toListVariables` (always `page: { number, size: 10 }` and the sort, the trimmed search, no empty search) plus `userId` when it is given. `utils/toCvDetailsPath` gives `/cvs/{id}/details`.
- `useCvs`: sends the `Cvs` query (`useCvs/cvs.graphql`) through the shared `usePagedList` and returns `cvs`, `total`, `loading`, `failed` and `retry`. `failed` hides the list, so a failed request never looks like an empty list. `retry` repeats the same request, so search, sort and page stay.
- `components/CvsTable`: the shared `DataTable` with the columns Name (sortable), Education and Employee (the owner email, for both roles; hidden below 1024px, as in the Figma tablet frame). The description sits in the detail line under each row, in the secondary colour (Figma), drawn by `components/CvsTable/CvDescription`. Each row has the shared `Menu` with `View`, `Edit` and `Delete` (Delete in the error colour); the button is named `Actions for {CV name}`. A click on a row calls `onView`, like `View`. `Edit` opens the Update CV modal and `Delete` opens the Delete CV modal.
- `components/CvsTable/CvDescription`: the description of a CV, copied from `ProjectDescription` of the projects feature. On a tablet (up to 1023px) it is cut after three lines with an ellipsis. When it is cut, a click (or Enter, Space) shows all of it and the next click cuts it again (`role="button"`, `aria-expanded`). When nothing is cut (a short text, or a desktop, which shows the full text as in Figma), it is plain text with the normal cursor. `useClampedText` measures the text, also on a resize. The line is a separate table row, so a click on it never opens the CV. A click on the menu button or on a menu item does not open the CV either (only View does); tests cover both.
- View: without an `onView` prop, `Cvs` opens `/cvs/{id}/details` with the locale-aware router (`useRouter` of `@/shared/i18n`).
- Search: the shared `SearchField` (debounced 300 ms, Enter at once, 100 characters at most). The backend matches the name, and for an Admin also the owner email, without regard to case. The field sits outside the error state, so an error does not remove the typed text.
- Sort: only Name sorts (the backend accepts no other field). The page starts sorted by Name ascending (`DEFAULT_CVS_SORT`).
- Pagination: the shared `Pagination`, 10 CVs on a page. It shows only for more than 10 CVs and uses the `total` of the backend.
- States: loading (skeleton inside the table, headers stay), empty (`You have no CVs yet`, only for a signed-in non-admin without a search and without `userId`; an admin and a list of one user show `No CVs found`, read with `useCurrentUser`; while the current user loads, the table shows the loading state, so the wrong text never flashes), no results for a search (`No CVs found`), error (`Failed to load CVs` and `Retry`). All use the shared `PageState`.
- `cvs.mocks.ts` and `cvForm.mocks.ts` (the form), `useDeleteCv/deleteCv.mocks.ts`: sample CVs, mocks of the `Cvs` query and `fakeBackendMock` (a stand-in backend for stories). For tests and stories only.
- Texts: `messages/` (`cvs` namespace, `en` and `pl`).
- Storybook: `Cvs.stories.tsx` (`Features/CVs/Cvs`): Desktop (1440px), Tablet (768px), ManyPages, SearchAndSort, NoResults, OfOneUser, Loading, Empty, LoadFailed and Polish.
- Used by: `app/[locale]/(app)/cvs/page.tsx`. Backend: `cvs` query (`backend/src/modules/cvs/README.md`).
- Docs: [docs/pages/20-cvs-page.md](../../../../docs/pages/20-cvs-page.md).

## Create CV and Update CV

Spec: [docs/pages/20-cvs-page.md](../../../../docs/pages/20-cvs-page.md), sections Create CV and Update CV.

`Cvs.tsx` owns one hook per modal and passes it to the modal: `CREATE CV` calls `creation.open()`, the `Edit` row action calls `editing.open(cv)`.

| Export                        | Purpose                                                                                                             |
| ----------------------------- | ------------------------------------------------------------------------------------------------------------------- |
| `useCreateCvForm()`           | Open state, form, submit and general error of Create CV. Returns `{ form, isOpen, open, setOpen, submit, failed }`. |
| `useUpdateCvForm()`           | The same shape. `open(cv: CvListItem)` fills the form with the CV.                                                  |
| `CreateCvModal({ creation })` | Title Create CV, buttons CANCEL and CREATE.                                                                         |
| `UpdateCvModal({ update })`   | Title Update CV, buttons CANCEL and SAVE. The fields hold the data of the CV.                                       |

Internal parts:

- `useCreateCv` and `useUpdateCv`: the `createCv` and `updateCv` requests. After success they load the open `Cvs` query again.
- `useCvForm`: React Hook Form with Zod. It holds the rules, blocks a double submit and shows server errors.
- `utils/cvForm.utils.ts`: `cvFormSchema` and the functions that make the request inputs.
- `components/CvFormFields`: Name, Education and Description fields. The modals do not repeat them.
- `cvForm.mocks.ts`: Apollo mocks and sample data for the tests.
- `messages/`: keys `cvs.form`, `cvs.create` and `cvs.update`.

Rules (the same in the backend):

- Name: required, 255 characters at most. Education: required, 255 characters at most. Description: required, 2000 characters at most. Text is trimmed.
- CREATE and SAVE are enabled only when the form is valid and the user changed it.
- A failed request keeps all values. A `BAD_USER_INPUT` error shows under its field. Other errors show one message in the modal.
- Success: the modal closes and a toast shows.

## Delete CV

- Delete: `Delete` in the row menu opens `components/DeleteCvModal` (the shared `ConfirmModal`): `Are you sure you want to delete CV {name}?` with the name in bold, `Confirm` and `Cancel`. `useDeleteCv` holds the chosen CV and sends the `deleteCv` mutation (`useDeleteCv/deleteCv.graphql`). Texts: `messages/` (`cvs.delete`, `en` and `pl`). Page document: [docs/pages/20-cvs-page.md](../../../../docs/pages/20-cvs-page.md), section Delete CV (AC-30 to AC-36, AC-39).
- Exports: `useDeleteCv({ page, rowsOnPage, onPageChange })` returns `{ cv, pending, askToDelete(cv), cancel(), confirm() }`; `DeleteCvModal({ cv, pending, onConfirm, onCancel })`.
- While the request runs, CONFIRM shows its loading state and a second press sends nothing (the hook and `ConfirmModal` both block it).
- Success: the CV leaves the Apollo cache (the row goes at once), the `Cvs` query loads again for the new total, the modal closes. `confirm` resolves `true` after a successful delete, `false` otherwise. The hook goes back one page when the user deletes the only CV on page 2 or later: it calls `onPageChange(page - 1)` after the delete succeeds (as `Projects.tsx` does in `handleConfirmDelete`). The page passes the current `page`, the number of rows it shows (`rowsOnPage`) and its `setPage`; nothing else is needed.
- The modal keeps the last CV name while it fades out. Vitest cannot see the fade (jsdom has no animation).
- Failure: the modal closes and an error toast shows the reason. The toast stays behind an open modal where a keyboard user cannot reach it, so the modal closes first.
  - `NOT_FOUND` (the CV is deleted, or it belongs to another user; the backend gives the same answer): the text `This CV does not exist any more. The list was updated.` The hook also loads the `Cvs` query again.
  - `FORBIDDEN`: the text `You are not allowed to delete this CV.`
  - Any other failure (network, server): `Something went wrong. Please try again.`
  - The backend message is never shown. `readFailure` (`shared/failures`) returns the kind, and the hook picks the translated text: `notFound` and `forbidden` have their own text, every other kind shows the general one.
- Who may delete (AC-32, AC-33, AC-34): the backend decides. A user deletes only their own CVs, an admin any CV. The frontend shows `Delete` for every row it receives, because the list already holds only rows the user may see.

## CV Details: loading one CV

Spec: [docs/pages/21-cv-details-page.md](../../../../docs/pages/21-cv-details-page.md) (PLAN S7.2, KAN-113). The page is built in steps; this is the data part.

- `useCv(id)` sends the `Cv` query (`useCv/cv.graphql`) and returns `cv`, `loading`, `failure` and `retry`. `failure` is `undefined` when the request worked. `retry` repeats the request for the same id.
- `useCv` reads a failed request with `readFailure` (`shared/failures`) and returns `notFound`, `forbidden` or `failed`:
  - `notFound`: the backend code `NOT_FOUND`. It also means the CV belongs to another user (the backend gives the same answer, so a user cannot learn which ids exist). The page must not try to tell the two cases apart.
  - `forbidden`: the backend code `FORBIDDEN`. The `cv` query does not send it today; the page is ready for it.
  - `failed`: any other code, or a network error. Only this kind shows Retry, because a repeat cannot change the answer of the other two.
- `useCv/cv.mocks.ts`: `cvMock`, `cvCodeErrorMock` and `cvNetworkErrorMock`. For tests and stories only.
- `useCvPreview(cvId)` sends the `CvPreview` query (`useCvPreview/cvPreview.graphql`, with `locale` of `useLocale`: the backend writes the open period as `Till now` or `obecnie`, so a language change is a new request) and returns `preview`, `loading`, `failed`, `unauthorized` and `retry`. The backend puts the whole CV together (details, skill groups, projects, languages, name and position), so the page never builds it from other requests. `unauthorized` is true for `NOT_FOUND` and `FORBIDDEN` (a missing CV and the CV of another user look the same). Retry cannot help there. `failed` is true for network and server errors and is the only case with Retry. `loading` is true again during a retry. The type is `CvPreviewData` (`cvs.types.ts`). Spec: [docs/pages/24-cv-preview-page.md](../../../../docs/pages/24-cv-preview-page.md).
- `components/CvPreview({ cvId })` (KAN-160): the content of the Preview tab. It calls `useCvPreview` and shows the CV as a printable document (Header, General, Summary, Skills, Projects, Professional skills table), or the loading, unauthorized (no Retry, no CV data) or error (with Retry) state, all through the shared `PageState`. Texts: `cvs.preview.states`. The page `h1` is the CV name of `CvLayout` (`PageHeader`), so the document starts with `h2`. Above the document is the EXPORT PDF button (S7.6, KAN-119), see `useExportCvPdf` below. See `components/CvPreview/README.md`.
- `useExportCvPdf(cvId)` (S7.6, KAN-119) sends the `ExportCvPdf` query (`useExportCvPdf/exportCvPdf.graphql`) and returns `exporting` and `exportPdf`. The query sends `locale` (`useLocale`), so the fixed texts of the PDF are in the language of the page (`en` or `pl`). The backend makes the PDF from the same data as the preview and checks access, so the page never builds the file. The answer has `fileName` (from the CV name) and `base64`. The hook decodes the text (`base64ToPdfBlob`, a pure util in `utils/cvPdf.utils.ts`, with a plain byte loop) and starts the browser download with `useSaveFile()` (hook `useSaveFile/`, because it adds a link to the page and sets a timer). `CvPreview` calls `useExportCvPdf` and gives `exporting` and `onExport` to `CvPreviewExport` as props. Only one request runs at a time (the ref `inFlight` guards the same tick). The request uses `no-cache`, so the large base64 text is not kept in the Apollo cache. A failure shows a toast (`cvs.preview.export`: `failedText` for network and server errors, `notFound` and `forbidden` for those codes) and the page stays where it is. No success toast: the download is the sign of success.
- `useExportCvPdf/exportCvPdf.mocks.ts`: `exportCvPdfSample`, `exportCvPdfMock`, `exportCvPdfCodeErrorMock` and `exportCvPdfErrorMock`. For tests and stories only.
- `useCvPreview/cvPreview.mocks.ts`: `cvPreviewSample`, `cvPreviewMock`, `cvPreviewCodeErrorMock`, `cvPreviewForbiddenMock` and `cvPreviewErrorMock`. For tests and stories only.
- `useCvDetailsForm(cv)`: the form of the Details tab. It reuses `useCvForm` (rules, double-submit guard, server errors) and `useUpdateCv`. Returns `{ form, failed, submit, canUpdate, isSubmitting }`. `canUpdate` is true only when the form is valid, differs from the saved CV and no request runs. After a successful save the values of the backend become the new unchanged state (UPDATE is disabled, the values stay). A failed save resets nothing. The success toast reuses the `cvs.update.success` texts.
- `components/CvDetailsForm({ details })`: the Name, Education and Description fields (`CvFormFields`) with the UPDATE button below. The button shows its spinner while the request runs and stays focusable. Text: `cvs.details.update` (`en`, `pl`). The form uses `noValidate`: the messages come from the form hook. A field shows its error after the user leaves it (`useZodForm` validates on touch).

- `components/CvLayout({ cvId, children })`: the shell of all four tabs, used by `app/[locale]/(app)/cvs/[cvId]/layout.tsx`. `useCvLayout` (next to it) loads the CV with `useCv`, reads the route (`usePathname` of `@/shared/i18n`) and builds the tabs and the breadcrumbs `CVs › {CV name} › {tab}` (the name in red, as in Figma). The `view` is one of:
  - `ready`: the tab page (`children`) shows. This is the only view that shows it, so a direct link to `/cvs/{id}/skills` of another user's CV cannot get around the access check.
  - `loading`: the skeleton, with the tabs. Data wins over `loading`: a refresh in the background does not replace a page that is shown.
  - `failed`: `Failed to load CV details` with Retry. `notFound` and `forbidden`: the shared `ErrorScreen` (`CV not found` or `No access`) with a link back to `/cvs`, without Retry, the tabs and the CV name.
- `components/CvDetails({ cvId })`: the Details tab. It reads the CV with `useCv` (the cache has it, so no second request) and shows `CvDetailsForm`. It shows nothing when there is no CV.
- Routes: `cvs/[cvId]/layout.tsx` (the shell), `details/page.tsx` (`CvDetails`). `skills/page.tsx` renders `CvSkills` (S7.3) and `projects/page.tsx` renders `CvProjects` (S7.4b), see below. `preview/page.tsx` renders `CvPreview` (S7.5, KAN-160); the shell gives it the breadcrumbs and the tabs.
- Texts: `cvs.tabs` (the four tab names and the navigation label) and `cvs.details` (`update`, `states`, `notFound`, `forbidden`), `en` and `pl`.
- Storybook: `components/CvLayout/CvLayout.stories.tsx` (`Features/Cvs/CvLayout`): Ready, Loading, NotFound, Forbidden, LoadFailed and Polish. `components/CvDetailsForm/CvDetailsForm.stories.tsx` (`Features/Cvs/CvDetailsForm`): Default, Changed, Invalid and Polish. The active tab in the shell stories depends on the mocked route (`nextjs.navigation.pathname`); not compared with Figma.
- Route and tab helpers: `CV_TABS` (`cvs.constants.ts`), `CvTab` (`cvs.types.ts`) and `utils/toCvTabPath(cvId, tab)`.

## CV Skills (S7.3, KAN-114)

Spec: [docs/pages/22-cv-skills-page.md](../../../../docs/pages/22-cv-skills-page.md). Backend: `backend/src/modules/cvs/README.md` (section CV skills). The tab is `components/CvSkills` (route `cvs/[cvId]/skills`). Everything that only this tab uses lives inside it (fractal layout).

- `CvSkills({ cvId })`: loads the skills, groups them by category, and shows ADD SKILL and REMOVE SKILLS. States: loading (skeleton, actions disabled), empty (`No skills added yet`, ADD SKILL stays available), error (`Failed to load skills` and Retry). The list stays on screen while a later request runs (`useCvSkills` returns `skills` as long as it has them), so a change does not blink the page.
- `components/SkillGroups`: the categories as headings with their skills below. `SkillItem` is one `<button>`: the bar (`MasteryBar`), the name, and the level in words for screen readers (`TypeScript Mastery: Advanced`). In the selection mode it has `aria-pressed`. The bar follows the design: five levels, each with its own colour and fill (`cvSkills.constants.ts`, `MASTERY_LEVELS`).
- Hooks (each one holds a modal flow and its request):
  - `useCvSkills(cvId)`: the `CvSkills` query. `useAvailableCvSkills(cvId, enabled)`: the `AvailableCvSkills` query. It sends nothing while the Add modal is closed and always asks the backend again when it opens (`network-only`).
  - `useAddCvSkill(cvId)`: Add skill. The options come from the backend, so the page never filters them. `Skill is required` shows for an empty choice, `CONFLICT` and `BAD_USER_INPUT` show under the field, other errors show once in the modal. A failed request keeps the chosen skill. Only success closes the modal.
  - `useUpdateCvSkill()`: Update skill. The Skill field is disabled (page doc). The mastery is the one value that changes, so SAVE is enabled only when it differs from the saved one and no request that changes nothing is sent.
  - `useRemoveCvSkills(cvId)`: the selection mode and the confirmation. A skill is chosen by the id of its CV-skill link. CANCEL and Escape leave the mode. A failed request keeps the choice. `NOT_FOUND` loads the list again and leaves the mode.
  - `useMasteryLabel()`: the translated level name.
- `utils/groupSkillsByCategory` (keeps the order of the backend, so no empty category). The hooks read a failed request with `readFailure` (`shared/failures`: `notFound`, `forbidden`, `conflict`, `invalid`; anything else is a friendly general text).
- UI changes come only after the backend answered. Add loads the list again. Update shows the cached skill that the answer changed. Remove leaves the skills out of the cached list when the answer arrives (`cache.modify`), then loads the list again.
- Texts: `cvs.skills` (`en`, `pl`). Mocks for tests and stories: `cvSkills.mocks.ts`.
- Storybook: `CvSkills.stories.tsx` (`Features/Cvs/CvSkills`): Desktop, Tablet, Loading, Empty, LoadFailed, SelectionMode, AddSkillModal, UpdateSkillModal, RemoveSkillsModal and Polish.
- E2E: `e2e/cvs/cv-skills.spec.ts` (empty state, the owner rule, add, update, remove, Escape, admin, another user's CV).

## CV Projects (S7.4b, KAN-116)

Spec: [docs/pages/23-cv-projects-page.md](../../../../docs/pages/23-cv-projects-page.md). Backend: `backend/src/modules/cvs/README.md` (section CV projects). The tab is `components/CvProjects` (route `cvs/[cvId]/projects`). Everything that only this tab uses lives inside it (fractal layout).

- `CvProjects({ cvId })`: the search field and ADD PROJECT above the table, then `CvProjectsTable`. The backend searches (name and domain, without case) and sorts (name, start date, end date); the page never filters or sorts the rows it holds. The search field sits outside the error state, so an error does not remove the typed text. States: loading (skeleton inside the table, headers stay; shown while there is no answer for the current search and sort, so a reload after a change does not blink the table), empty (`No projects added yet`, ADD PROJECT stays), no results (`No projects found`, the search text stays), error (`Failed to load projects` and Retry). The not found and no access states belong to `CvLayout`: it shows this tab only after the backend returned the CV.
- `components/CvProjectsTable`: the shared `DataTable`. Columns Name and Domain (from the catalog project), Start Date and End Date (from the CV; an empty end date shows `Present`). The Domain column hides below 1024px, like in the Projects table. Under each row is a detail line (Figma frame-46): the description of the catalog project (shared `ProjectDescription`) and the responsibilities of the CV as filled tags (`ResponsibilityTags`, one tag per line of the text, `utils/toResponsibilityTags`). **There is no Responsibilities column any more**: Figma has none, and Figma wins over the page doc (decided 2026-11-23; the doc `docs/pages/23-cv-projects-page.md` and AC-3 are changed). The table has no line under the last row (`lastRowLine={false}`). Each row has the shared `Menu` with `Update` and `Delete`; the button is named `Actions for {project name}`.
- Hooks (each one holds a flow and its request):
  - `useCvProjects(variables)`: the `CvProjects` query. `useCvProjectsListState()`: search and sort. `utils/toCvProjectsVariables` trims the search and leaves out an empty one.
  - `useAvailableCvProjects(cvId, enabled)` and `useProjectRoles(enabled)`: the options of the Add and Update modals. They send nothing while the modal is closed. The projects ask the backend again each time the modal opens (`network-only`), because the answer depends on the projects the CV holds now.
  - `useCvProjectForm(rangeOf)`: the form that Add and Update share (React Hook Form and Zod). It holds the rules, blocks a double submit and maps a failed request: `BAD_USER_INPUT` field errors show under their field, anything else becomes one general message.
  - `useAddCvProject(cvId)`: the open state, the chosen project and the `addCvProject` request. The options come from `availableCvProjects(cvId)`: the backend leaves out the projects that the CV holds (AC-31), so the page never filters. Choosing a project fills the two dates with its days. The server checks the duplicate again (`CONFLICT`), and the options load again after it.
  - `useUpdateCvProject()`: `open(cvProject)` fills the form with the current data. The input has no project: the project of an entry cannot change. SAVE needs a change (`isDirty`).
  - `useRemoveCvProject(cvId)`: the confirmation and the `removeCvProjects` request (a list with one id). The project leaves the list only after the backend answered (`cache.modify`, then the list loads again). The project of the catalog stays.
- `utils/cvProjectForm.utils.ts`: `cvProjectFormSchema` (project and start date required, both dates inside the days of the project, the end date not before the start date, at least one role, responsibilities at most 2000 characters), `toProjectRange`, `toCvProjectFormValues`, `toAddCvProjectInput` and `toUpdateCvProjectInput`. Dates go to the backend as midnight UTC (`toUtcDateIso`, now in `@/shared/utils` with `fromUtcDateIso` and `formatCalendarDate`; the Projects page uses them too). The hooks read a failed request with `readFailure` (`shared/failures`: `notFound`, `forbidden`, `conflict`, `invalid` or `unknown`) and pick the translated text.
- `components/CvProjectFormFields`: Project, Domain, Start Date, End Date, Description, Environment, Roles and Responsibilities. Domain, Description and Environment come from the catalog project: they are disabled and are not part of the form values. The date pickers block days outside the project, and each one also stops at the other date (`toDateLimits`): the End Date calendar offers no day before the Start Date, the Start Date calendar none after the End Date. A typed date outside these limits is ignored by the picker like any text that is not a date, so a typed End Date before the Start Date leaves the field empty (the form rule `End date cannot be earlier than start date` stays as a second guard). The three modals (`AddCvProjectModal`, `UpdateCvProjectModal`, `RemoveCvProjectModal`) only hold the buttons and the title.
- UI changes come only after the backend answered. Add loads the list again. Update shows the cached entry that the answer changed, and loads the list again (a new date can change the order). A failed request keeps every typed value.
- Texts: `cvs.projects` (`en`, `pl`). Mocks for tests: `cvProjects.mocks.ts`.
- E2E: `e2e/cvs/cv-projects.spec.ts` (table, search, sort, update, remove, Escape, empty CV, an admin adds a project). The helper `e2e/support/cvProjects.ts` adds projects through the API with an admin session.

## Notes

- **Signed-out users on the CV Details page.** The spec lists authentication errors as a separate case. `readFailure` has no kind for it: a code like `UNAUTHENTICATED` becomes `unknown` (`failed` on this page). This is decided: the page relies on `shared/apollo/sessionLink`, which refreshes the session, runs the request once more and redirects to sign-in when the session is over (PLAN D9). The session link keeps the request pending while the redirect is under way, so this page stays on its loading state and shows no error screen before sign-in (checked in `e2e/cvs/cv-session-end.spec.ts`, also with a slow sign-in page).
- **The description is a `role="button"` on a `<p>`**, like in projects (the same known issue). A real `<button>` would be cleaner.
- **Two copies of `useClampedText`.** `ProjectDescription` is shared now (`shared/components/ProjectDescription`, used by Projects and CV projects), but `CvDescription` of the CVs list still has its own copy of the hook and CSS. Replace it with the shared component. The 1023px limit is written in CSS only (no breakpoint token yet).
- **A click on the description line does nothing for a CV that is not cut.** The row above opens the CV. This is the decided behaviour.
- **The Employee column shows the owner email for both roles.** The page document says the same, so there is no role check in the frontend.
- **Search, sort and page are not in the URL.** They are lost on a refresh and cannot be shared (same as the projects page).
- **Not checked in a browser.** Vitest and Storybook (Chromium) pass; nobody has compared the page with the Figma frame pixel by pixel, or used it with a screen reader or on a touch screen.
- **E2E:** `e2e/cvs/cvs.spec.ts` covers the list (admin and user), sort, search, row click, the menu, create, update, delete and the go-back-one-page rule. It does not cover the Polish texts, the tablet layout or the keyboard (no `cvs.a11y.spec.ts` yet).
- **Dark and light theme of the description line.** It uses `--color-text-secondary`; check the contrast against the Figma frame.
- **The Create form has no owner field.** On `/cvs` it sends no `userId` and the backend uses the signed-in user. On the User CVs tab (S7.7, KAN-120) `Cvs` gets `userId` from the route and `useCreateCvForm(userId)` adds it to the `createCv` input (`toCreateCvInput(values, userId)`). Never take it from the form. `useUpdateCvForm(userId)` and `useDeleteCv({ userId })` send the same `userId` as a scope, so the backend rejects a CV of another employee. With `userId`, `View` and a row click open `/cvs/{id}/preview?from=...` (`toCvTabPath(id, tab, from)`, `toUserCvsPath`); `CvLayout` reads `from` with `toCvReturnPath` (an allowlist, see the user-details README) and keeps it in its tabs and in the CVs breadcrumb. The tab is in `features/user-details`; its open notes (search by owner email, View) are in its README.
- **The `NOT_FOUND` reload of a delete has no test** (`useDeleteCv.test.tsx` holds an `it.todo` with the steps; the hook needs an active `Cvs` query).
- **The fade-out of the delete modal and the real backend were not checked by hand.**
- **Stale total after a delete (fixed here, check the projects page).** `useDeleteCv` drops every cached `cvs` page when a CV is deleted. Before this, going back one page showed page 1 from the cache with the old total, so a second page button stayed for 10 CVs (found by the E2E test). `useDeleteProject` uses the same refetch of the open query only; it was not checked for the same problem.
- **The shared `Tabs` differ from Figma on the CV Details page.** Figma shows four tabs of the same width (about 150px) with the line under the first one; the shared `Tabs` size each tab by its text with a 24px gap. Not changed here, because the other pages use `Tabs` too (check with the design).
- **The Preview tab page is a placeholder** (`null`). It shows the shell and an empty area until S7.5.
- **CV Details is not checked in a browser.** Vitest passes; nobody has compared the page with the Figma frame, tried a tablet width, a screen reader or the dark theme. The form is 852px wide and centred, as measured on the 1440px frame.
- **E2E:** `e2e/cvs/cv-details.spec.ts` covers the CV shell: breadcrumbs, the four tabs, the fields, UPDATE (disabled until a change, saved after a reload), the required-field message, the tab route after a reload, the CV not found view for another user's CV, and an admin who opens a user CV. It does not cover the Polish texts, the tablet layout or the keyboard.
- **The build fails if the route params are read outside `<Suspense>`.** Next.js 16 treats `params` as runtime data. Read them in a small inner component wrapped in `<Suspense>` (see `cvs/[cvId]/layout.tsx`). Only `pnpm build` and the E2E run find this; the typecheck, the lint and the unit tests do not.
- **A CV name that is very long** is not cut in the breadcrumbs (no ellipsis rule in Figma). Check how it wraps.
- **`features/skills` does not exist yet (KAN-108).** The ticket says S7.3 reuses it "in CV mode". It is not built, so the CV Skills tab has its own `SkillGroups`, `SkillItem` and `MasteryBar` inside `components/CvSkills`. When KAN-108 builds the same grouped list for the Skills page and the User Skills tab, move these three parts to the nearest common ancestor and use one copy.
- **The first modal with a `Select` found a bug in the shared `Select`.** Its list had no `z-index`, so the modal overlay (20) covered it and no option could be clicked. It now has 21 (see the Select README). Unit tests and Storybook did not show it; only the E2E test did.
- **The Update modal has a Mastery field that the page doc does not list.** The doc says the Skill field is disabled and "SAVE sends the mutation when an updateable skill property exists". The ticket names `updateCvSkill` (mastery per CV), so Mastery is that property. Without it the modal would have nothing to change. Confirm with the team.
- **The Add modal has an optional Mastery field that the page doc did not list.** Figma shows the mastery in the Add modal and Figma wins (agreed with Rafal). The field is optional: with no choice the request has no `mastery` and the backend copies the level of the owner. With a choice the request sends it. The page doc 22 now lists the field.
- **Not checked in a browser by a person.** Vitest, Storybook (Chromium) and the E2E test pass. Nobody compared the tab with the Figma frame (bar sizes, spacing, colours of the five levels), used it with a screen reader, on a touch screen or in the dark theme. The five bar colours follow the design picture; the match of each colour to a level is a reading of that picture.
- **The list does not reload by itself** when the owner's skills change in another tab. The options of the Add modal are loaded each time it opens; the list loads again only after the user's own change or a retry.
- **ADD SKILL and REMOVE SKILLS show for every user who can open the CV.** The backend lets the owner and an admin change the CV, and everybody who sees the CV is one of them, so no role check is made in the frontend. An unverified email gets `FORBIDDEN` from the backend; the modals show a message for it.
- **No `maxLength` on the number of skills in the UI.** The backend accepts at most 100 ids in one remove. A CV with more than 100 chosen skills would be refused as `BAD_USER_INPUT` (general text).
- **KAN-156, catalog for employees (done).** The Add project modal used the admin only `projects` query, so a user who is not an admin got `FORBIDDEN`. It now uses `availableCvProjects(cvId)` (owner or admin of the CV). The `HeldCvProjects` query and the `CATALOG_PAGE` limit are gone. The E2E spec has a test where an Employee adds a project to their own CV.
- **KAN-156, the options list has no paging and no search.** `availableCvProjects` returns every project that can be added, by name. The page document has no search field in the Add modal. A catalog with many projects needs a search argument in the backend query and a field in the modal.
- **KAN-116, own choice: the dates are filled when a project is chosen.** The page document says that choosing a project fills `Project Start Date` and `Project End Date`, and that the CV dates are editable. This was read as: both date fields start with the days of the project, and the user narrows them. The date pickers are disabled until a project is chosen, because the days only make sense inside a project. Confirm with the team.
- **KAN-116, the date picker blocks days outside the project.** A typed date outside the days is not accepted by the picker, so the message `End date must be within project duration` shows for a value the picker does not block (and for a `BAD_USER_INPUT` answer of the backend). The form rules still say it as text, and a unit test covers it.
- **KAN-116, no end date means Present.** The backend allows an empty end date, and the Add and Update forms leave End Date optional. The table shows `Present`. The page document says only "if End Date is optional in the domain model".
- **KAN-116, no "active" role flag.** `ProjectRole` has no active flag in the backend, so the Roles field offers every role of the catalog.
- **KAN-116, the Roles multi-select closes the whole modal on Escape** while its list is open, because the Escape key reaches the modal too. This is the behaviour of the shared `MultiSelect` inside `Modal`; not changed here.
- **KAN-116, not checked in a browser by a person.** Vitest and the E2E spec pass. Nobody compared the tab with the Figma frame (column widths, the modal), used it with a screen reader or on a touch screen, or checked the tablet layout and the dark theme. The page has no Storybook stories yet.
- **KAN-116, no pagination.** The backend returns the whole list and the page document has no pager. A CV with very many projects shows all rows.
- **A CV list request with an unknown employee (`NOT_FOUND`) shows the general error with Retry.** The backend answers `NOT_FOUND` for an unknown `userId` (create and list). The create modal shows its general message and keeps the typed values. The list has no own text for it (`FORBIDDEN` has: `states.forbidden`). Retry cannot help here; add a text only if the team wants one. `UNAUTHENTICATED` still shows the general error until the global handler exists (see the first note).
- **The `<h1>` of `Cvs` is hidden when `userId` is set**, because the User Details shell already shows the page title. This is decided.
