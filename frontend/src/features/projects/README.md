# Projects

The `/admin/projects` page (PLAN S5.5b, KAN-102): the global list of projects, for Admin users.

- Exports: `Projects` (the whole page content; the route only renders it).
- `useProjectsListState`: holds the choices of the user: `search`, `sort` and `page`. A new search or sort goes back to page 1. Nothing is filtered or sorted in the frontend.
- `utils/toProjectsVariables`: turns that state into the query variables. It always sends `page: { number, size: 10 }` and the sort, trims the search, and leaves out an empty search. The page size 10 is one rule: the backend default (`DEFAULT_PAGE_SIZE` in `common/pagination`) and the frontend `DEFAULT_PAGE_SIZE` are both 10, and a test checks the size that is sent. (The backend accepts `sort: null` too, since the `resolveSort` fix.)
- `useProjects`: sends the `Projects` query (`useProjects/projects.graphql`) with those variables and returns `projects`, `total`, `loading`, `failed` and `retry`. `failed` hides the list, so a failed request never looks like an empty list. `retry` repeats the same request, so search, sort and page stay.
  - **Note for the next list page** (users, skills, languages): this hook has the same `loading`, `failed` and `retry` shape that every list query needs. Do not copy it a second time. When a second list page needs it, move one shared hook to the nearest common ancestor (`PLAN.md` S5.9) and let `useProjects` call it.
- `components/ProjectsTable`: the shared `DataTable` with the columns Name, Domain, Start Date and End Date. `EnvironmentTags` draws the technologies as tags. `utils/formatProjectDate` formats a date with `Intl` and the language of the page (`MM/DD/YYYY` in English, `DD.MM.YYYY` in Polish, no code for a new language). A date that cannot be read shows a dash with the screen reader text `Date not available`, never an empty cell.
- `components/ProjectsTable/ProjectDescription`: the description of a project. On a tablet (up to 1023px) it is cut after three lines with an ellipsis. When it is cut, a click (or Enter, Space) shows all of it, and the next click cuts it again. When nothing is cut, it is plain text with the normal cursor. `useClampedText` measures the text, also on a resize.
- Search (KAN-128): the shared `SearchField` (debounced 300 ms, Enter at once, 100 characters at most) sends the text to the backend, which matches name and domain without regard to case. The field sits outside the error state, so an error does not remove the typed text.
- Sort (KAN-128): Name, Start Date and End Date sort on the backend; the arrow in the header shows the direction. The page starts sorted by Name ascending (`DEFAULT_PROJECTS_SORT`), and the Name header shows it at once. A click cycles ascending, descending, ascending. There is no "no sort" state, so the order is always visible.
- Pagination (KAN-128): the shared `Pagination`, 10 projects on a page. It shows only for more than 10 projects, and uses the `total` of the backend. While a page loads, it keeps the last `total`.
- Row menu (KAN-129): each row has the shared `Menu` (three dots) in the `DataTable` `renderRowActions` slot, with `Edit` and `Delete` (Delete in the error colour). The button is named `Actions for {project name}`, so a screen reader tells the rows apart. `ProjectsTable` takes `onEdit(project)` and `onDelete(project)`. `Projects.tsx` passes the real handlers: Edit opens the update modal (KAN-132, below) and Delete opens the delete modal (KAN-130, below). Only one menu is open at a time; it closes on Escape (the focus returns to the button), on a click outside and after a selection, and the keyboard opens it (Enter or Space), moves (arrows) and selects (Enter). This is Radix `DropdownMenu` behaviour, covered by `ProjectsTable.test.tsx`.
- Delete (KAN-130): `Delete` in the row menu opens `components/DeleteProjectModal` (the shared `ConfirmModal`): `Are you sure you want to delete project {name}?` with the name in bold, `Confirm` and `Cancel`. `useDeleteProject` holds the chosen project and sends the `deleteProject` mutation (`useDeleteProject/deleteProject.graphql`).
  - While the request runs, CONFIRM shows its loading state and a second press sends nothing (the hook and `ConfirmModal` both block it).
  - Success: the project leaves the Apollo cache (the row goes at once), the `Projects` query loads again for the new total, and the modal closes.
  - Last row of a page: when the user deletes the only project on page 2 or later, `Projects.tsx` goes back one page (`handleConfirmDelete`), so the page is never empty while earlier pages have projects. `useDeleteProject.confirm` resolves `true` after a successful delete, `false` otherwise.
  - The modal keeps the last project name while it fades out, so the text does not show `delete project ?`. Vitest cannot see the fade (jsdom has no animation); look at it in Storybook or a browser.
  - Failure: the modal closes and an error toast shows the reason. A `CONFLICT` error (the project is used in a CV, PLAN D18) shows the backend message as it is (`utils/toDeleteProjectFailure`). Any other failure shows the friendly text `Something went wrong. Please try again.` The modal closes because the error toast stays until closed, and a keyboard user cannot reach a toast behind an open modal (see the Toast README).
- Create (KAN-131): the `CREATE PROJECT` button (right end of the toolbar, shown also while the list loads or failed) opens `components/CreateProjectModal` (the shared `FormModal`): Name, Domain, Start Date, End Date, Description and Environment, with `Create` and `Cancel`. The flow is in `useCreateProjectForm` (open state and submit); the form with its rules is `useProjectForm` (React Hook Form + Zod through `useZodForm`), shared with Update; the fields are `components/ProjectFormFields`, also shared; the request is in `useCreateProject` (`useCreateProject/createProject.graphql`).
  - Rules (`utils/projectForm.utils.ts`, `projectFormSchema`, the same for Create and Update): name, domain, both dates and description required (Environment is optional); name and domain 100 characters, description 2000, texts trimmed; end date not earlier than start date (the same day is allowed, like the backend). The messages are the ones of the page document. `Create` is enabled when the form is valid and changed. The fields have no `maxLength`, so a pasted long text shows the message and is not cut silently.
  - Dates: the picker returns local midnight. `toUtcDateIso` sends midnight UTC of the same calendar day, because the backend keeps only the UTC day. A plain `toISOString` would save the day before for a user east of UTC. A test covers it.
  - Success: the `Projects` query loads again (the new project takes its place in the sort, search and page, and the total changes), the modal closes and a success toast shows. The form is empty each time the modal opens.
  - Failure: the modal stays open and every value stays. `BAD_USER_INPUT` field errors show under their field (`applyServerFieldErrors`); any other failure shows one message inside the modal (`role="alert"`). A toast is not used here, because an open modal hides the page and the toast from a keyboard user (see the Toast README); the delete flow closes its modal, this one cannot.
  - A second submit while the request runs sends nothing (`FormModal` and a guard in `useCreateProjectForm`). `useCreateProjectForm.test.tsx` sends two submits in one tick and checks that only one request goes out.
- Update (KAN-132): `Edit` in the row menu opens `components/UpdateProjectModal` (the shared `FormModal`, title `Update project`) with the same fields as Create, filled with the data of the row, and `Update` and `Cancel`. The flow is in `useUpdateProjectForm` (the project being edited, open state, submit); the form, rules and double submit guard are the shared `useProjectForm`; the request is in `useUpdateProject` (`useUpdateProject/updateProject.graphql`).
  - `Update` is enabled when the form is valid and changed, so an untouched form cannot be sent. The form is filled again from the row each time the modal opens.
  - Dates: the backend keeps midnight UTC, the picker shows local days. `fromUtcDateIso` turns the UTC day into the local day for the prefill (`new Date(iso)` would show the day before west of UTC), and `toUtcDateIso` does the way back, as in Create. Tests cover both.
  - **The technologies:** the backend replaces the WHOLE environment with `environmentIds` (the default is an empty list). The form starts with the ids of the row (`toProjectFormValues`), the user can add and remove technologies, and `toUpdateProjectInput` sends the form value, not the ids the project had. A test sends the exact input and a mock only matches that input.
  - Success: the `Projects` query loads again (a changed name or date can move the row), the modal closes and a success toast shows. Failure: like Create, the modal stays open, every value stays, `BAD_USER_INPUT` field errors show under their field and anything else as one message in the modal.
  - A second submit while the request runs sends nothing (`useProjectForm`; `useUpdateProjectForm.test.tsx` sends two submits in one tick).
- Environment field (KAN-136): `ProjectFormFields` shows the shared `MultiSelect` named `Environment` in both forms. The options come from `useEnvironmentOptions` (`useEnvironmentOptions/environmentOptions.graphql`, the backend `skills` query, Admin only, sorted by name). `loading`: the field is disabled and shows `Loading technologies`. `failed`: the field shows `The technologies could not be loaded.` and a `Retry` button; the rest of the form still works. The field is optional: `projectFormSchema` allows an empty list, at most 50 ids (`MAX_ENVIRONMENT_SKILLS`), each id once. Create sends the chosen ids (an empty list for none); Update sends the form value.
- States: loading (skeleton inside the table, headers stay), empty (`No projects found`), no results for a search (`No projects found`), error (message and `Retry`). All use the shared `PageState`.
- Texts: `messages/` (`projects` namespace, `en` and `pl`).
- Storybook: `Projects.stories.tsx` (`Features/Projects/Projects`) shows the page on a 1440px desktop and a 768px tablet viewport, with a project that has the longest allowed texts (name 100, domain 100, description 2000 characters, `maxLengthProject` in `projects.mocks.ts`), and the ManyPages, SearchAndSort, NoResults, Loading, Empty, LoadFailed and Polish versions.
- Contract: the backend `Project` has `environment { id name }`. The page document calls the same data `technologies`; the schema wins.
- Used by: `app/[locale]/(app)/admin/projects/page.tsx`. Backend: `projects` query, Admin only (KAN-101).
- Done: list, tags, three states (KAN-127); search, sort and pagination (KAN-128); row menu (KAN-129); delete (KAN-130). create (KAN-131); update (KAN-132); the Environment field in both forms (KAN-136).
- Docs: [docs/pages/27-projects-page.md](../../../../docs/pages/27-projects-page.md).

## Known issues

- **Environment field: chips need the skills list (KAN-136).** The chips take their names from the skills query. When that query fails, the Update form shows the error and a retry, no chips, but it still holds the ids of the project and sends them back, so an edit does not remove technologies. After a retry the chips show. A skill that is not in the list any more (deleted from the catalog) cannot show as a chip either. Fix it by merging the technologies of the edited project into the options if this matters to the designer.
- **Create: the pickers have no `minDate` or `maxDate`.** The DatePicker README advises passing the start date as the limit of the end picker. With a limit the picker treats a typed earlier date as "not a date", so the user sees "End date is required", not the "End date must be later than start date" of the page document. Without the limit, a day before the start can be picked in the calendar and the form then shows the right message. Change this if the designer prefers greyed-out days (then the message for a typed earlier date needs a change in the shared `DatePicker`).
- **The DatePicker texts are translated in this feature** (`projects.form.datePicker`, shared by Create and Update). Every form with a date picker needs the same eight texts. When a form in another feature needs them, move them to the common messages and pass them from there.
- **Update: not checked in a browser.** Vitest, E2E and Storybook stories (`UpdateProject`, `UpdateProjectFailed`, and for Environment `CreateProjectEnvironment`, `CreateProjectEnvironmentFailed`) cover it. Look at the modal as for Create (below). E2E covers a project with technologies (create with technologies, remove one with Update, and the chips of a seeded project, KAN-136).
- **Update: a project changed by someone else.** The form starts from the row as the list loaded it. If another Admin changes or deletes the project meanwhile, the update overwrites it, or the backend answers `Project not found` and the modal shows the general message. There is no version check. The same applies to the technologies: Update sends the form value of the Environment field (`toUpdateProjectInput`), which starts as the ids of the row as the list loaded it, so a change of technologies made by another Admin while the modal is open is overwritten without a message. Add a version check in the backend to fix it.
- **Create: not checked in a browser.** Vitest, E2E and two Storybook stories (`CreateProject`, `CreateProjectFailed`) cover it. Nobody has looked at the modal in a browser: check the two date fields side by side at 768px and 1440px, the calendar inside the modal (the popup must not be cut by the modal), the dark theme, and the focus return to the CREATE PROJECT button after closing. `e2e/projects/projects.spec.ts` has create tests (KAN-133), but they do not look at the layout.
- **Create: duplicate project names.** The page document does not say whether a name must be unique. The form shows whatever field error the backend sends. Confirm the rule with the backend side.
- **Description and tags sit in the Name cell.** The Figma list draws them on a full-width line under each project row. `DataTable` draws one line for each row, so they stack under the name and wrap inside the Name column. To match the design, give `DataTable` an optional detail line for each row (a change to the shared component).
- **Differences from the Figma list** (`docs/images/figma/desktop-1440/{light,dark}/frame-58.png`, `tablet-768/light/frame-53.png`, `tablet-768/dark/frame-51.png`; compared with the `Desktop` and `Tablet` stories, which use the same two projects):
  - Tablet: done. The Domain column is hidden and the description is cut after three lines (it opens on a click). The 1023px limit is our own choice: the repo has no breakpoint rule yet. The Domain column is hidden by its position in `ProjectsTable.module.css` (`nth-child(2)`), because `DataTable` cannot hide a column. It breaks if a column is added before Domain. Replace it when the `DataTable` ticket (a column option to hide below a width, and the detail line above) is done.
  - Desktop: Figma gives Domain a wide column (about 400px). The table gives the width to the Name column, so a domain such as `CRM (Customer RM)` wraps into three lines.
  - Dates: Figma writes `4/15/2025` without a leading zero on the Projects list. The table writes `04/15/2025` (the team decided on `MM/DD/YYYY`). The CV projects list in Figma has two digits. Confirm with the designer.
  - Text size: the project name is about 12px in Figma and 14px in the table. The tags are about 16px in Figma and 14px in the table.
  - Page title: Figma shows `Projects` as a small grey title in the top bar. The page shows a 24px heading.
  - Search field: Figma shows it at the left, 320px wide, with the CREATE PROJECT button at the right end. The field and the button match. Figma shows an arrow next to Name, Start Date and End Date at all times; the table shows it faint until the column is sorted.
  - Row menu: built (KAN-129). The CREATE PROJECT button is built (KAN-131) and sits at the right end of the toolbar, as in Figma. Delete is built (KAN-130). Edit is built (KAN-132).
- **Row menu: not checked in a browser.** The three-dot button is 40px square (`--space-10` in the shared `Menu`), which is below the 44px that many touch guidelines ask for. Check it on a touch screen and, if needed, enlarge the target in the shared `Menu` (not here). Also look at the menu in the 1440px and 768px Storybook views. The `Actions` header is hidden from sight by `DataTable`; a unit test cannot show this, so confirm it in Storybook.
- **Delete: not checked in a browser.** Tests (Vitest) cover the modal, the loading state, success, the `CONFLICT` message and a network error. Nobody has looked at the modal in Storybook, and `e2e/projects/projects.spec.ts` has delete tests (KAN-133): a project that no CV uses, a Cancel, and Banking Portal, which two seeded CVs use (the `CONFLICT` message shows and the row stays).
- **Delete: no Storybook story.** `Projects.stories.tsx` has no story for the modal or for a failed delete. Add them with the update modal slice.
- **Delete: a failed reload after a successful delete.** The row is removed from the cache before the list reloads. If the reload fails, the page shows the error state with `Retry`, although the project is deleted. This is correct but may confuse the user.
- **Sidebar link: done by the app layout (KAN-82).** `features/app-shell/navigation.constants.ts` lists `/admin/projects` for Admin users only (`ADMIN_EXTRA_NAV_ITEMS`). The page is a `div`, not a `main`: `AppShell` already renders the one `main` landmark. A second `main` was removed on the merge of `development` (2026-11-12).
- **No Admin check in the frontend (AC-1).** A non-admin user who opens the route gets an error state, because the backend rejects the query. No data leaks, but the message is not clear. The app layout and the session role now exist (`shared/session`, `app-shell`): add a route guard (redirect or a Forbidden state) in a follow-up ticket.
- **The delete double-click test needed a long mock delay (2026-11-12).** It failed once in a full run (a 50 ms mock answered before the `aria-busy` check). The delay is now 300 ms and the check uses `waitFor`. If a similar test is added, use the same pattern.
- **Search, sort and page are not in the URL.** They are lost on a refresh and cannot be shared. `SearchField` already takes a `defaultValue`, so the state can move to the URL later (the page document asks for no URL state).
- **The page shows no page buttons with the seed data.** The seed has 6 projects and the page holds 10. Pagination is covered by tests and by the `ManyPages` story; to see it in the app, add more than 10 projects.
- **Escape in the calendar closes the Create or Update modal too (KAN-134).** One Escape in the open calendar closes the calendar and the whole modal, so the user loses the entered values. WAI-ARIA wants the popup closed first. Radix `Dialog` listens for Escape on the document before the calendar sees it. Fix in the shared `Modal` / `DatePicker` (for example, `Modal` ignores Escape while a calendar is open). `e2e/projects/projects.a11y.spec.ts` has a `test.fixme` for it: remove the `fixme` when it is fixed.
- **Calendar header cut by the modal at 768px (KAN-134).** At 768 x 1024 the calendar opens above the End Date field and the top edge of the modal cuts its header: the month and year buttons and the arrows cannot be used (seen in the E2E run on 2026-11-12). It is a shared `DatePicker` / `Modal` issue (the popup is not in a portal). `projects.a11y.spec.ts` has a `test.fixme` for it.
- **Dark theme: the field labels have 4.32:1 contrast (KAN-134).** The label uses `--color-text-secondary` (`grey-400`) on `--color-modal-bg` (`grey-600`). WCAG AA needs 4.5:1. The light theme passes. Fix the token pair in `shared/styles/themes.css` (a design decision). The E2E contrast test checks this label in the light theme only.
- **Not checked by a tool: screen readers and touch.** KAN-134 checks keyboard use, focus return, both themes (text contrast of the list and of the modal title) and the 768px width in Playwright. Nobody has listened to the page with a screen reader or used it on a touch screen.
- **E2E covers the list, search, sort, pages, create, update and delete** (`e2e/projects/projects.spec.ts`, KAN-133) and keyboard use, focus return, the Light and Dark themes and the tablet width (`e2e/projects/projects.a11y.spec.ts`, KAN-134). It does not cover the description click (Storybook tests do). The a11y file changes no data, so it can run in parallel with the other file. The create, update and delete tests are in the same file as the list tests on purpose: tests of one file run one after another, and these tests add projects that the "6 seeded projects" checks must not see. A new project test must clean up with `deleteProjectsByName` in `afterEach`. The technologies tests use the seeded skills (React, Docker) and the six technologies of the seeded Banking Portal.
- **Pagination is not in the page document.** `docs/pages/27-projects-page.md` has no page size and no pagination section. The size 10 comes from PLAN D19 and the backend default (both 10). Ask for a line in the page document.
- **Two utils files with almost the same name.** `utils/projects.utils.ts` (query variables) and `components/ProjectsTable/utils/project.utils.ts` (date and tag helpers) differ by one letter. Rename one of them when one of the two is touched next.
- **`ProjectDescription` uses `role="button"` on a `<p>`.** It has `tabIndex`, `aria-expanded` and Enter and Space handling, so it works. A real `<button>` would be cleaner, and the missing date dash could use hidden text instead of `role="img"` (`ProjectsTable.tsx`).
- **The tablet limit 1023px is written in two CSS files** (`ProjectsTable.module.css`, `ProjectDescription.module.css`). Move it to one place when the repo gets a breakpoint token.
