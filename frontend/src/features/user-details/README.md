# User Details

The shell of the pages `/users/{userId}/...` (PLAN S6.2, KAN-105), the Profile tab (S6.3, KAN-105; avatar upload S6.3b, KAN-106) and the CVs tab of a user (PLAN S7.7, KAN-120).

- Exports: `UserLayout` (header, breadcrumbs and tabs; used by `app/[locale]/(app)/users/[userId]/layout.tsx`), `UserProfile` (content of the Profile tab; used by `.../[userId]/profile/page.tsx`) and `UserCvs` (content of the CVs tab; used by `.../[userId]/cvs/page.tsx`).
- `UserLayout`: the shared `PageHeader` and `Tabs`. Tabs: Profile, Skills, Languages and CVs (`USER_TABS`). The CVs tab is shown to an Admin only (`getUserTabs`). The breadcrumbs are `Employees › {name} › {tab}`; the name is highlighted, not a link, like the CV name in `CvLayout`, and it is the email for a user who has not filled in a name (`getUserDisplayName`). The title and the tab name follow the route. Each tab is a link, so the URL keeps the employee and the tab after a refresh.
- Data (PLAN D6, SSR): the route layout preloads `me` and `user(id)` (`user.graphql`, all fields the Profile tab needs) with `PreloadQuery`, and `useUserLayout` reads them with `useSuspenseQuery`. So the server HTML already has the name and, for an Admin, the CVs tab; the browser sends no request of its own for them. Tests render the layout inside `<Suspense>` and an awaited `act()`.
- States (KAN-105), as Figma shows them (no in-shell error screens there): while loading, the one `<Suspense>` of the `(app)` layout shows the loading `PageState` on a full load; the user routes have no boundary of their own (`instant = false` on the layout and on the tab pages that wait for data), so a client navigation keeps the old page until the new one is ready, like the list pages (KAN-172). An unknown user (`NOT_FOUND`, or `BAD_USER_INPUT` for an id that is not a UUID: `isUserNotFound`) calls `notFound()`, so the full-screen 404 page shows; during server rendering already, so the first HTML is the 404 page. Any other failure is thrown to the full-screen "Oops" page (`app/[locale]/error.tsx`, RETRY). `errorPolicy: "all"` only lets `useUserLayout` tell the two apart. A preload that fails on the server is sent again by the browser (one extra request, on errors only).
- `UserProfile` (KAN-105, content of the Profile tab; used by `.../[userId]/profile/page.tsx`): the avatar (initials), the name, the email and "A member since …" (`formatMemberSince`: language of the page, UTC, so the server and the browser show the same day). `useUserProfile` reads the same `user(id)` query as the shell, so it gets the preloaded result and sends no request. The page also preloads the Department and Position options of the form for every viewer (`departmentOptions` / `positionOptions`, any signed-in user; `@/shared/catalogOptions`).
- Avatar (KAN-106, PLAN D11; values in `docs/design-tokens.md` › "Avatar upload"): `ProfileAvatar` shows the photo (`user.avatarUrl`, `?v=` changes with each upload) or the initials. The owner or an Admin (`canEdit`) also gets `AvatarUpload` next to it (a label for a visually hidden file input; PNG, JPG or GIF up to 5 MB, `AVATAR_MAX_BYTES`) and, with a photo, the red Remove × on it. `useAvatarActions` runs one action at a time and ends each in a toast: upload (`checkAvatarFile` first, then `POST /api/users/{id}/avatar`) and remove (`DELETE`), both through `requestAvatar` (a 401 refreshes the session and tries once more; an ended session goes to sign-in). After success the `User` query loads again and the stored `users` lists are removed, so the Users table shows the new photo. The sidebar keeps the initial (Figma).
- `ProfileForm` (inside `UserProfile`): First Name, Last Name, Department, Position (rules from `@/shared/userProfile`). Editable for the owner or an Admin (`canEditProfile`); anyone else sees the same fields read-only (`readonly` / `aria-readonly`, still focusable) and no buttons. The values are in the server HTML too (`defaultValue` on the inputs, the chosen label inside the shared `Select`). UPDATE is disabled until a trimmed value changes; it sends `updateProfile` (`useUpdateProfile`: the cached `User` updates itself, `users` lists are evicted, the own profile also updates the cached `me` names) and shows a toast. Errors: field errors from the backend under the field, any other failure above the buttons (`FormErrorMessage`, `readFailure`).
- VERIFY EMAIL (left of UPDATE): only the owner whose email is not verified (`canVerifyEmail`, from `me.isVerified`). `useVerifyEmailRequest` sends `resendVerificationCode` and opens `/verify-email`; a code sent less than a minute ago (`RESEND_COOLDOWN`) opens it too, with an info toast; already verified hides the button; any other failure shows an error toast. It never marks the email as verified itself (AC-27).
- `UserCvs`: `RequireAdmin` around `Cvs` with `userId` from the route. The list, search, sort, pages, Create CV, Update CV and Delete CV are the ones of `features/cvs`. The owner of a new CV is the `userId` of the route (`useCreateCvForm(userId)`); the form has no owner field.
- Texts: `messages/` (`userDetails` namespace, `en` and `pl`).
- Access, two layers: the proxy treats `/users/{id}/cvs` as admin-only and redirects anyone else to `/users` (`shared/session/utils/session.utils.ts`); `RequireAdmin` is the message behind it. The backend decides: `cvs` and `createCv` with a `userId` are for an Admin only.
- Docs: [docs/pages/14-user-cvs-page.md](../../../../docs/pages/14-user-cvs-page.md); the Profile tab: [docs/pages/11-user-profile-page.md](../../../../docs/pages/11-user-profile-page.md).
- Stories: `UserLayout` (Admin, Employee, Loading, Polish), `UserProfile` (owner not verified, Admin, Admin with a photo, read-only, read-only with a photo, new user, options failed, tablet, Polish), `AvatarUpload` and `ProfileAvatar`. E2E: `e2e/user-profile/user-profile.spec.ts` and `e2e/user-cvs/user-cvs.spec.ts`.

## Things to note

- **One shell for all tabs.** KAN-105 built the S6.2 shell on top of the minimal one from KAN-120 (one `layout.tsx` for `/users/[userId]`). The Skills and Languages pages are still empty placeholders (`app/[locale]/(app)/users/[userId]/placeholderPage.tsx`); replace it per tab when that tab is built.
- **Read-only fields use Figma's grey (about 1.2:1), below WCAG 4.5:1**, by the user's choice (`docs/design-tokens.md`). The read-only stories run the a11y check as a warning only.
- **The Profile tab reads `me` with `useSuspenseQuery`, while the sidebar still uses `useQuery`**, so the browser can send one `Me` request of its own. The `(app)`-wide `me` preload belongs to the SSR ticket.
- **`user-details.mocks.ts` has no test of its own.** It holds fixed data only, with no logic (same as `features/cvs/cvs.mocks.ts`); the component tests use it. Add a test if logic is added there (as `projects.mocks.test.ts` does).
- **The employee is also sent when a CV is opened (KAN-173).** `useCv` takes the employee from `from` and sends it as `userId` with the `Cv` query, so a CV of another employee shows `CV not found` (AC-12).
- **The employee is sent with every change.** `Cvs` sends the `userId` of the route with `createCv` (the owner), `updateCv` (`input.userId`) and `deleteCv` (`userId`). The last two are only a scope: the backend answers `NOT_FOUND` for a CV of another employee (KAN-120, agreed with Rafal; see the backend CVs README). The value comes from the route, never from the row.
- **Search also matches the owner email (decided, KAN-120, PLAN D36).** For an Admin the backend searches the name and the owner email (S7.1). The page document of this tab says name only. The team decided to keep both: it is harmless on this tab (all rows have one owner) and useful on `/cvs`. Do not change it without asking.
- **View keeps the employee context.** `View` on the tab opens `/cvs/{id}/preview?from=%2Fusers%2F{userId}%2Fcvs`. `CvLayout` (`useCvLayout`) reads `from`, checks it with `toCvReturnPath` and then: the first breadcrumb `CVs` leads back to that tab, and the CV tabs (Details, Skills, Projects, Preview) keep `from` in their links. `toCvReturnPath` accepts only `/users/{id}/cvs` (letters, digits, `-` and `_` in the id); anything else (another site, `//host`, extra parts, a query) is dropped, so the link cannot be an open redirect. Not covered: a page reload of a CV tab keeps `from` (it is in the address), but a `NOT_FOUND` or `No access` screen of the CV still links to `/cvs`.
- **Search, sort and page are not in the URL** (same as the CVs page), so a refresh keeps the employee and the tab, but not the search.
- **The CVs tab has no story and no Polish E2E.** Its component tests and `e2e/user-cvs/user-cvs.spec.ts` cover English only.
