# Users module

The users list, the admin user management and the profile (PLAN.md S6.1, S6.3, §8). Reading is for every signed-in user; create, update and delete are for admins; the owner or an admin updates a profile. Sign-up, sign-in and sessions stay in the `auth` module.

- **GraphQL:**
  - `users(search, sort, page)` returns a `UserPage` `{ items, total }` for the Users page. `user(id)` returns one `User` for User Details (`NOT_FOUND` when missing). A `User` has `id`, `email`, `firstName`, `lastName`, `role`, `department { id name }`, `position { id name }` and `createdAt` (the profile's "Member since"). Names, department and position are `null` for a user who signed up and has not filled in the profile yet. There is no field for the password hash (users page AC-18, AC-26).
  - `createUser(input: { email, password, firstName, lastName, departmentId, positionId, role })`, `updateUser(input: { id, firstName, lastName, departmentId, positionId, role })` return the `User`. `deleteUser(id)` returns `true`.
  - `updateProfile(input: { id, firstName, lastName, departmentId, positionId })` returns the `User` (User Details, Profile tab).
- **REST:** `GET` / `POST` / `DELETE /api/users/:id/avatar` for the profile photo: see [avatars/README.md](avatars/README.md).
- **Search:** split into words; each word must be in the first name, the last name or the email, without regard to letter case ("alpha lim" finds Alpha Lima). `%`, `_` and `\` are plain characters (`escapeLike`).
- **Sort:** `firstName` (default, ascending), `lastName`, `department`, `position` (by the name of the department or position), then by id. Any other field gives `BAD_USER_INPUT`. Empty values follow PostgreSQL on every column: last in A→Z, first in Z→A (Prisma cannot set "nulls last" on a relation's column, so one rule for all).
- **Create:** the email is trimmed and lowercased (like sign-up, so sign-in finds it); the password follows D33 (8–128 characters with a letter and a digit, stricter than the page's "at least 6") and is stored only as an argon2 hash; names are trimmed, required, at most 100 characters. The user starts verified (D16).
- **Update:** names, department, position and role. Email and password are not in the input (users page AC-25); a password change has its own flow.
- **Update profile:** the Update fields without the role (`UpdateProfileInput` = `UpdateUserInput` minus `role`), with the same checks. The owner or an admin may save; anyone else gets `FORBIDDEN`, also for an unknown id, so a user cannot probe which ids exist. An admin gets `NOT_FOUND` for an unknown id. It runs inside the same row lock as update (with `ownerMayAct`), so an admin demoted at the same moment cannot still edit someone else. No verified email needed (D16).
- **Delete:** the database cascade removes everything the user owns: CVs with their skills and projects, user skills and languages, avatar, codes and sessions (D13). The session ends at once: the auth guard reads the user from the database on every request, as it does for the role.
- **Errors:**
  - Unknown department or position → `BAD_USER_INPUT` with a field error on `departmentId` / `positionId` ("Department not found", "Position not found"), both at once. Checked before the write; a delete between the check and the write (`P2003`) gives the same error.
  - Email taken (unique index, `P2002`) → `CONFLICT` with `reason: "EMAIL_TAKEN"`, the same reason as sign-up.
  - Unknown user → `NOT_FOUND` "User not found".
  - PostgreSQL stopped the transaction because a parallel one needs the same rows (a deadlock or write conflict, `P2034`, e.g. a delete while the user's browser refreshes its token), or Prisma rolled it back because it did not finish in time (`P2028`, default 5 s) → `CONFLICT` with `reason: "CONCURRENT_CHANGE"` ("The user was changed at the same time. Try again"). Nothing was saved, so the frontend can offer a retry and show its own text for the reason.
- **D24, `CONFLICT` with a `reason`:**
  - `SELF_DELETE`: an admin deletes themselves. Checked inside the lock, like `OWN_ROLE`, so both mutations check in the same order: `FORBIDDEN`, `NOT_FOUND`, then `CONFLICT`.
  - `OWN_ROLE`: an admin removes their own Admin role.
- **The last admin (D24)** needs no count and no own reason. Update and delete first lock the actor's and the target's rows (`SELECT … FOR NO KEY UPDATE`, one statement in id order, so no deadlock; it does not block the light lock a refresh-token insert takes, so sign-in and refresh never wait for an admin edit), then check and write in the same transaction. The actor must still be an admin inside the lock (`FORBIDDEN` otherwise: the guard checked the role before the request waited), and cannot demote or delete themselves. So every change keeps its actor an admin, and at least one admin always remains. Two admins who demote or delete each other at the same moment run one after the other; the second is no longer an admin and gets `FORBIDDEN`. Without the lock both could win and leave no admin; the integration tests send such requests in parallel.
- **Authorization:** the global guard needs a signed-in user for everything; `@Roles(Role.ADMIN)` on `createUser`, `updateUser` and `deleteUser`. `updateProfile` has no role limit: the service checks owner or admin. Reading and the profile need no verified email (D16 does not list them).
- **Tests:** `*.spec.ts` next to the code; `backend/test/users/users.int-spec.ts` runs every operation over HTTP against the test database, including the parallel D24 cases.
- **Docs:** [Users page](../../../../docs/pages/10-users-page.md) · [PLAN.md S6.1, D13, D16, D24, D33](../../../../PLAN.md)

## Things to note

For the Users page (frontend) and for S6.3. Found in the review of KAN-103. None of them blocks this module.

- **The reasons arrive as `CONFLICT`, not as field errors.** `applyServerFieldErrors` handles only `BAD_USER_INPUT`. The Users page maps the reasons in its own utils file, as sign-up and the Languages catalog do. Suggested places: `EMAIL_TAKEN` under the email field of Create user, `OWN_ROLE` under the role field of Update user, `SELF_DELETE` and `CONCURRENT_CHANGE` as a general error in the modal. `FORBIDDEN` is the page-level no-access state.
- **The signed-in admin's own row.** The backend refuses `SELF_DELETE` and `OWN_ROLE`. The page should also disable Delete and the role change for the row of the signed-in admin, so the buttons match the permissions.
- **`User` has no `isVerified` and no avatar field.** `createdAt` was added in KAN-105 ("Member since"). The verification status comes from `me.isVerified`: only the owner sees VERIFY EMAIL, so `User` needs no `isVerified` (decided in KAN-105).
- **Avatar.** The REST endpoints (D11) are not built, and `User` has no flag that tells whether an avatar exists. Until S6.3 the table can show initials only. Decide in S6.3 whether to add `hasAvatar`, or to accept one failed image request for each user without an avatar.
- **`updateUser` needs every field, the role included.** A user who signed up has no names, department or position (all `null`). The Update user modal then opens with empty required fields, and the admin must fill them in. This matches the users page document.
- **A page can become empty.** After the last user of the last page is deleted, `users` returns `{ items: [], total }` and no error. `Pagination` shows the last page as current but does not call `onPageChange`, so the page must set its own page state back.
- **The password rule is D33, not the page document.** The users page document says at least 6 characters (AC-16 and the example message). The backend accepts 8 to 128 characters with a letter and a digit. The Create user form uses the shared `passwordProblem`, so it does not show the 6-character message.
