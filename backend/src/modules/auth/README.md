# Auth module

Sign-up, sign-in, sign-out, token refresh, email verification, password reset and change, and the current user. Sets the session cookies and registers the global sign-in guard (D9, D10).

- **Folders:** one sub-folder per topic, each with its own `dto/` and specs: `sessions/` (tokens, cookies, `JwtAuthGuard`), `verification/` (email code), `password-reset/` (forgot and reset). Sign-up, sign-in, sign-out, refresh, `me` and `password.ts` (argon2 hashing, used by the root and `password-reset/`) stay in the module root.
- **GraphQL:** `signIn(input)` returns `SessionUser` and sets the cookies. `signUp(input)` does the same for a new user. `signOut` ends the session and clears the cookies. `refresh` swaps the refresh cookie for new cookies and returns `true`. `me` returns `SessionUser` or `null`. All five are `@Public()`. `signIn` and `signUp` are also throttled (see below).
- **Sign-up:** `signUp(input: { email, password })` checks a valid email and a password of 8 to 128 characters with at least one letter and one digit (D33). `signIn` keeps 6 to 128, so older accounts can still sign in. It saves the email in lower case and the password as an argon2id hash, with the default role `USER` and `isVerified: false`. Then `VerificationService.issueCode` mails the first code, and the user is signed in with cookies, but is not verified yet (D16). The unique index on `email` decides between two parallel requests. A taken email gives `CONFLICT` with `extensions.reason: EMAIL_TAKEN` and the message `An account with this email already exists`. If the mail cannot be sent, the account stays and the error is logged without the code; the user asks for a new code with `resendVerificationCode`.
- **Email verification (D20):** `verifyEmail(input: { code })` and `resendVerificationCode` act on the signed-in user, who may not be verified yet, so they are not `@Public()`. Both use `GqlThrottlerGuard`. `VerificationService.issueCode` creates the code and mails it; `signUp` calls it for the first code.
  - **Code:** 6 digits from `crypto.randomInt`, valid 10 min, single use. Only a keyed hash is stored (`VerificationCode.codeHash`). The code is never logged.
  - **Tries:** at most 5 per code (`attempts`). The try is counted before the code is compared, in one statement, so parallel requests cannot go over the limit. Then the user must request a new code.
  - **Resend:** one code per 60 s, counted from `createdAt`. A new code deletes the older ones. `createdAt` and `expiresAt` come from `Clock`, never from the database clock.
  - **Errors:** every error has `extensions.reason`: `CODE_INVALID`, `CODE_EXPIRED`, `CODE_USED` (all `BAD_USER_INPUT`), `TOO_MANY_ATTEMPTS`, `RESEND_COOLDOWN` (`TOO_MANY_REQUESTS`), `ALREADY_VERIFIED` (`CONFLICT`). A user who is already verified cannot use either mutation.
  - **`@Verified()`:** the guard and `EMAIL_NOT_VERIFIED` are in [common/auth](../../common/auth/README.md).
- **Password reset (D20, D22, D33):** `forgotPassword(input: { email })` and `resetPassword(input: { token, newPassword })`. Both are `@Public()` and use `GqlThrottlerGuard`. Both return `true`. `PasswordResetService` holds the rules.
  - **`forgotPassword`:** answers `true` for every valid email, also an unknown one, and then sends no mail, so the answer never shows who is registered. For a known email it deletes the older tokens, stores a new one and mails the link. A failed mail is logged (message only, never the token) and does not change the answer.
  - **Known trade-off:** a new `forgotPassword` request deletes the older links of that user. Anyone who knows an email can therefore end the link the user waits for. `GqlThrottlerGuard` limits how often this can happen.
  - **Token:** 32 random bytes (`crypto.randomBytes`), valid 1 h, single use. Only a keyed hash is stored (`PasswordResetToken.tokenHash`). `createdAt` and `expiresAt` come from `Clock`.
  - **Old rows:** used and expired rows stay in `PasswordResetToken` until the same user asks for a new link or resets the password. A cleanup job for old rows is not built yet.
  - **`resetPassword`:** checks the token, then in one transaction marks it used, saves the new password hash, deletes the other tokens of the user and deletes all refresh tokens of the user (D22). Two parallel requests cannot both use one token. It does not sign the user in: the page sends the user to Sign In.
  - **Password rule:** 8 to 128 characters with a letter and a digit, the same as sign-up (D33).
  - **Errors:** `BAD_USER_INPUT` with `extensions.reason` `RESET_TOKEN_INVALID`, `RESET_TOKEN_EXPIRED` or `RESET_TOKEN_USED`. The reason does not say which user owns the token.
- **Change password (D22, D33):** `changePassword(input: { currentPassword, newPassword })` returns `true`. Signed-in users only, verified or not (no `@Verified()`), and throttled by `GqlThrottlerGuard`.
  - **Rules:** `currentPassword` is 1 to 128 characters (an older password may be weaker than D33); `newPassword` follows D33 and must differ from the current one. `AuthService.changePassword` checks the current password, then the difference (in that order, so a wrong guess always gets the same answer), then in one transaction saves the new hash, raises `tokenVersion` and deletes all refresh tokens of the user.
  - **Parallel changes:** the new hash is saved only if the stored hash is still the one that was checked. A parallel password change or reset, or a deleted user, gives `UNAUTHENTICATED` (session ended), not a server error.
  - **Sessions:** every other session ends at once (see the token version below). This session gets new cookies with a new token family, so it keeps working.
  - **Errors:** a wrong current password gives `BAD_USER_INPUT` with `extensions.reason: CURRENT_PASSWORD_INCORRECT` (not `UNAUTHENTICATED`, which the frontend reads as an ended session); a new password equal to the current one gives `BAD_USER_INPUT` with `extensions.reason: NEW_PASSWORD_SAME`. Without a session: `UNAUTHENTICATED`.
- **Token version:** `User.tokenVersion` is a claim in the access token. `changePassword` and `resetPassword` raise it, and `JwtAuthGuard` rejects an access token whose version differs, so old access tokens stop working before they expire. Each refresh token also stores the version it was made with, and `refresh` deletes the family of a token with an older version: a refresh that ran during a password change can write its new token after the change deleted the others, and this ends it.
- **Password rule:** `dto/password-rule.ts` (`@PasswordRule()`) holds D33 for sign-up, reset and change.
- **Cookies:** `access_token` (JWT, 15 min, holds only the user id and the token version) and `refresh_token` (random, 7 days). Both are `HttpOnly`, `SameSite=Lax`, and `Secure` in production.
- **Refresh token:** only its HMAC hash is stored in `RefreshToken`. `signOut` deletes the whole token family.
- **`JwtAuthGuard`:** global. Reads the access cookie, loads the user from the database and sets `request.user`. Without a valid session, only `@Public()` resolvers pass. It must run before `RolesGuard` and `VerifiedGuard`, so `AppModule` imports `AuthModule` before `ApiConventionsModule` (`app.module.spec.ts` checks this).
- **Refresh (D21):** `refresh` marks the used token as replaced (`replacedAt`) and issues a new token in the same family (`familyId`). A replaced token works once more (`graceUsedAt`) inside 30 s (`REFRESH_GRACE_WINDOW_MS`), so a parallel request does not sign the user out. A second use inside the window, or any use after it, deletes the whole family. When the session has ended, `refresh` answers `UNAUTHENTICATED` and clears both cookies.
- **Throttling (D23):** `signIn` uses `GqlThrottlerGuard` from [common/throttling](../../common/throttling/README.md): `TOO_MANY_REQUESTS` after the limit. `verifyEmail` and `resendVerificationCode` use it too. `signUp`, `forgotPassword`, `resetPassword` and `changePassword` use it too.
- **Errors:** wrong email or wrong password both give `UNAUTHENTICATED` with `Invalid email or password`.
- **Tests:** `*.spec.ts` next to the code; `backend/test/auth/`: `auth.int-spec.ts`, `sign-up.int-spec.ts`, `auth-guards.int-spec.ts`, `refresh.int-spec.ts`, `verification.int-spec.ts`, `password-reset.int-spec.ts`, `change-password.int-spec.ts` and `throttling.int-spec.ts` run over HTTP against the test database.
