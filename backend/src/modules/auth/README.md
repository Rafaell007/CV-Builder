# Auth module

Sign-in, sign-out, token refresh, email verification and the current user. Sets the session cookies and registers the global sign-in guard (D9, D10).

- **GraphQL:** `signIn(input)` returns `SessionUser` and sets the cookies. `signOut` ends the session and clears the cookies. `refresh` swaps the refresh cookie for new cookies and returns `true`. `me` returns `SessionUser` or `null`. All four are `@Public()`. `signIn` is also throttled (see below).
- **Email verification (D20):** `verifyEmail(input: { code })` and `resendVerificationCode` act on the signed-in user, who may not be verified yet, so they are not `@Public()`. Both use `GqlThrottlerGuard`. `VerificationService.issueCode` creates the code and mails it; `signUp` will call it for the first code.
  - **Code:** 6 digits from `crypto.randomInt`, valid 10 min, single use. Only a keyed hash is stored (`VerificationCode.codeHash`). The code is never logged.
  - **Tries:** at most 5 per code (`attempts`). The try is counted before the code is compared, in one statement, so parallel requests cannot go over the limit. Then the user must request a new code.
  - **Resend:** one code per 60 s, counted from `createdAt`. A new code deletes the older ones. `createdAt` and `expiresAt` come from `Clock`, never from the database clock.
  - **Errors:** every error has `extensions.reason`: `CODE_INVALID`, `CODE_EXPIRED`, `CODE_USED` (all `BAD_USER_INPUT`), `TOO_MANY_ATTEMPTS`, `RESEND_COOLDOWN` (`TOO_MANY_REQUESTS`), `ALREADY_VERIFIED` (`CONFLICT`). A user who is already verified cannot use either mutation.
  - **`@Verified()`:** the guard and `EMAIL_NOT_VERIFIED` are in [common/auth](../../common/auth/README.md).
- **Password reset (D20, D22, D32):** `forgotPassword(input: { email })` and `resetPassword(input: { token, newPassword })`. Both are `@Public()` and use `GqlThrottlerGuard`. Both return `true`. `PasswordResetService` holds the rules.
  - **`forgotPassword`:** answers `true` for every valid email, also an unknown one, and then sends no mail, so the answer never shows who is registered. For a known email it deletes the older tokens, stores a new one and mails the link. A failed mail is logged (message only, never the token) and does not change the answer.
  - **Token:** 32 random bytes (`crypto.randomBytes`), valid 1 h, single use. Only a keyed hash is stored (`PasswordResetToken.tokenHash`). `createdAt` and `expiresAt` come from `Clock`.
  - **`resetPassword`:** checks the token, then in one transaction marks it used, saves the new password hash, deletes the other tokens of the user and deletes all refresh tokens of the user (D22). Two parallel requests cannot both use one token. It does not sign the user in: the page sends the user to Sign In.
  - **Password rule:** 8 to 128 characters with a letter and a digit, the same as sign-up (D32).
  - **Errors:** `BAD_USER_INPUT` with `extensions.reason` `RESET_TOKEN_INVALID`, `RESET_TOKEN_EXPIRED` or `RESET_TOKEN_USED`. The reason does not say which user owns the token.
- **Cookies:** `access_token` (JWT, 15 min, holds only the user id) and `refresh_token` (random, 7 days). Both are `HttpOnly`, `SameSite=Lax`, and `Secure` in production.
- **Refresh token:** only its HMAC hash is stored in `RefreshToken`. `signOut` deletes the whole token family.
- **`JwtAuthGuard`:** global. Reads the access cookie, loads the user from the database and sets `request.user`. Without a valid session, only `@Public()` resolvers pass. It must run before `RolesGuard` and `VerifiedGuard`, so `AppModule` imports `AuthModule` before `ApiConventionsModule` (`app.module.spec.ts` checks this).
- **Refresh (D21):** `refresh` marks the used token as replaced (`replacedAt`) and issues a new token in the same family (`familyId`). A replaced token works once more (`graceUsedAt`) inside 30 s (`REFRESH_GRACE_WINDOW_MS`), so a parallel request does not sign the user out. A second use inside the window, or any use after it, deletes the whole family. When the session has ended, `refresh` answers `UNAUTHENTICATED` and clears both cookies.
- **Throttling (D23):** `signIn` uses `GqlThrottlerGuard` from [common/throttling](../../common/throttling/README.md): `TOO_MANY_REQUESTS` after the limit. `verifyEmail` and `resendVerificationCode` use it too. `forgotPassword` and `resetPassword` use it too. `signUp` gets the same guard when it is built.
- **Errors:** wrong email or wrong password both give `UNAUTHENTICATED` with `Invalid email or password`.
- **Tests:** `*.spec.ts` next to the code; `backend/test/auth.int-spec.ts`, `auth-guards.int-spec.ts`, `refresh.int-spec.ts`, `verification.int-spec.ts`, `password-reset.int-spec.ts` and `throttling.int-spec.ts` run over HTTP against the test database.
